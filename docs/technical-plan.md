# 企业售后工单智能处理系统 v0.1.0 技术方案

> 日期：2026-11-18。技术栈与两阶段范围按本轮讨论固定；本文其余细化内容作为开发基线，涉及效果的结论仍需实测。不代表功能已实现。
> 项目定位：面向企业售后场景的课题原型，采用模拟数据验证。以现有 aftersales 为取数与诊断能力基础，接入企业售后知识库。
> 本文只定义产品范围、技术设计、分阶段交付和验证方向；不修改现有代码，不包含真实企业业务收益。

执行时优先阅读：3.1 技术选型→14 工程与环境→15 数据/API→16 图与恢复→18 开发顺序→19 验收。第 1～13 章保留产品与设计理由，后续实施细节集中在第 14～20 章。

## 1. 定位与范围

### 1.1 产品定位

系统首先是功能型售后工单工作台。业务人员创建工单，系统执行知识检索、数据查询和故障调查，展示节点状态、证据及处理方案。无法自动处理的工单进入 Human-in-the-Loop（HITL）节点，由人工接管。

第二阶段增加自研 App 客服问答入口和渠道适配。消费者先获得有依据的自动回答；无法解决时，系统将会话和调查结果持久化为人工工单，告知客户已记录、已转人工。人工在工作时间处理，并通过渠道返回后续结果。

“客服数字人”在本方案中首先指文字问答与状态反馈入口；虚拟形象、语音合成、音视频交互不属于首版范围。飞书更适合作为内部通知或业务人员入口；面向消费者优先考虑自研 App，电商平台按可用接口适配。不将“所有客服问题都来自群聊”作为设计前提。

### 1.2 核心场景

| 场景 | 主要数据 | 预期产出 |
|---|---|---|
| 产品与操作咨询 | 产品手册、FAQ、型号与版本 | 有来源的回答、操作步骤 |
| 设备故障调查 | 客户反馈、日志、埋点、已知故障资料 | 原因判断、证据、下一步处理建议 |
| 售后政策咨询与申请 | 政策、购买与设备信息 | 适用条款、缺失材料、人工处理建议 |

投诉可作为工单的附加意图和优先级信号。自动执行退款、换货、补发等具有业务副作用的操作不进入首版；资料齐全也不能越过审批权限。

### 1.3 两阶段边界

| 阶段 | 产品目标 | 主要交付 |
|---|---|---|
| 第一阶段 | 手动创建→自动调查→人工接管→结果确认 | 工单工作台、节点运行、知识检索、日志适配、HITL、基础经验记录、可回放轨迹 |
| 第二阶段 | 自动接收问题、自动回答与人工工单衔接，开展效果评测 | App 问答入口、渠道适配、结果回传、经验发布与复用、知识库及编排对照评测 |

两阶段都记录执行成本和结果。第一阶段先验证正确性和闭环；第二阶段开展系统性对照评测，不把评测埋点拖到第二阶段才建设。

## 2. 现有能力与复用边界

以下为静态代码与文档核对结果，不代表外部接口当前可用。

| 现有内容 | 可复用方式 | 产品化补充 |
|---|---|---|
| `faq-triage`、FAQ、`SUPPORT_KB.md` | FAQ 数据作为首批知识语料，脚本作为参考行为基线 | 企业知识由知识服务提供，避免提示词、关键词表与知识库多处维护 |
| `fetch-full-log/scripts/fetch_log.py` | 按邮箱查反馈、下载解压日志，或接收日志直链 | 封装工具接口、统一错误类型、隔离工单文件、核对反馈与故障时间 |
| WiFi 取数与诊断脚本 | 保留可确定执行的取数、归一化及规则诊断 | 将机器结果与最终客户回复分离，保留诊断版本 |
| Android/iOS 领域 Skill | 复用领域分析方法与受控参考资料 | 将自由 Shell 操作收敛为授权的文件检索、时间窗抽取和诊断工具 |
| 源码同步脚本 | 作为研发辅助能力参考 | 首版不要求每张工单拉源码；必要且有访问条件时按品牌、版本固定代码快照 |

现有日志链路为：登录后台→调用 `getFeedbackPageList`（参数包含 email/page/pageSize）→取得反馈及日志链接→下载解压→输出日志文件路径。它查询用户已提交的反馈，不意味着只凭邮箱就能取得任意时段的设备日志。

默认只取最新一条反馈不适合作为所有工单的最终策略。适配层应结合发生时间、设备、平台和版本筛选；存在多个可能对象时请求确认，不能按邮箱直接认定日志属于本次故障。接口正式文档、授权方式、排序与限流约定均需在真实接入前核验。

现有脚本对“查询失败”和“没有日志”的降级处理需要重新区分；现有路由与 BOT_SETUP 中的日志优先级描述也需统一。首版以本系统的编排规则为准，不直接拼接现有多份提示词作为运行控制。

## 3. 总体架构

```text
第一阶段：业务人员创建工单
第二阶段：App 会话／其他授权渠道事件
                  ↓
接入层：校验、身份关联、幂等入库、附件登记
                  ↓
请求解析节点：规则提取＋结构化模型输出
                  ↓
编排 Agent ←────────────── Case 状态与执行记录
  ├─ 知识调查子任务 → 知识服务 → 原文、版本、适用条件
  ├─ 故障调查子任务 → 受控工具 → 反馈、日志、诊断证据
  ├─ 方案生成节点 → 结构化方案与回复草稿
  └─ 检查／决策 → 继续、生成方案、追问、转人工
                  ↓
工作流执行器：参数校验、权限、预算、超时、检查点
                  ↓
待确认方案／HITL 待办／已确认结果
                  ↓
异步经验提取 → 候选经验 → 验证发布 → 后续检索复用
```

系统采用“受约束的 Agent 编排＋确定性执行器”。模型可以选择已注册的调查动作，程序控制状态转移、工具执行、重试和人工接管。第一阶段采用集中式任务委派，不建设 Agent 之间自由互聊的通信网络。

知识服务使用统一接口。首版知识结构与后续实体属性实验共用调用边界，避免更换知识库结构时重写工单流程。

### 3.1 已确定的技术选型

本节按用户确认固定。依赖具体补丁版本由 P00 兼容性试验后锁定，不在未运行安装与试验时声称版本组合可用。后续调整需在本文写明原因，不在开发中自行切换框架。

| 模块 | 选择 | 理由 |
|---|---|---|
| 后端 API 与模型输出校验 | Python、FastAPI、Pydantic | 便于封装现有 Python 取数脚本和结构化协议 |
| 数据访问与迁移 | SQLAlchemy＋Alembic | 明确事务与迁移版本，业务表由迁移管理 |
| 状态与业务数据 | PostgreSQL | 统一承载业务表和 LangGraph 检查点，表及连接职责分开 |
| Agent 框架 | LangGraph StateGraph＋专业子图 | 显式条件流转、持久检查点、人工中断；不采用自由群聊式协作 |
| 异步执行 | 独立 Worker＋数据库任务表 | 原型先控制依赖；任务落库，不依赖请求进程中的临时后台任务 |
| 前端 | Vue 3＋TypeScript＋Vite＋Element Plus | 表单、工单表格、抽屉、节点时间线与人工审核；不建设拖拽编排器 |
| 附件 | 工单隔离的文件存储，数据库保存引用与校验值 | 原型可本地存储，后续替换对象存储 |
| 知识索引 | 应用层中文分词与 BM25＋pgvector＋RRF＋可开关重排序 | 小规模原型减少独立服务，保留型号与错误码的精确匹配 |
| 模型接入 | 统一模型客户端，按任务角色配置模型 | 支持同模型基线及轻量／较强模型对照，不绑定特定供应商 |

不要求现有纯标准库 Skill 安装这些依赖。新增应用层与原脚本分离，脚本通过适配层调用；第一阶段可先使用 Mock Adapter。

相对早期草稿，将 MySQL 改为 PostgreSQL：采用 LangGraph 后优先使用官方 PostgreSQL 检查点组件，并以 pgvector 承载向量数据，避免原型同时维护多个数据库服务。业务事务与检查点保存仍是不同边界，不因使用同一数据库就自动原子提交。

第一阶段不引入 Redis、Celery、ES、Milvus 或图数据库。首版后台由独立 Worker 从 PostgreSQL 任务表取任务；确认存在吞吐瓶颈后再评估队列组件。技术选型依据见附录 B。

## 4. 节点与 Agent 的职责

### 4.1 请求解析不是 Agent

请求解析包括两类工作：邮箱、附件、时间格式等由代码校验；问题意图、现象、用户已尝试操作等由结构化 LLM 调用抽取。输出 JSON 是数据对象，不是生成可执行代码。

```json
{
  "intents": ["device_fault"],
  "symptoms": ["frequent_disconnect"],
  "customer_ref": "customer_demo_01",
  "product_model": null,
  "platform": "android",
  "occurred_at": null,
  "attempted_actions": [],
  "missing_fields": ["product_model", "occurred_at"]
}
```

未知字段保留 null 并记录来源，不能凭模型常识补成事实。字段来自用户、接口或人工修正时分别记录 provenance。缺失字段是否阻塞某个动作，由该动作输入要求决定，不要求一次补齐所有字段。

### 4.2 角色划分

| 角色 | 职责 | 是否独立循环 |
|---|---|---|
| 请求解析节点 | 输出结构化请求 | 否 |
| 编排 Agent | 根据目标、当前证据和未完成事项，决定调查动作与终止方式 | 是，受预算和节点白名单限制 |
| 知识调查 Agent | 对明确的知识子任务执行检索、必要的改写、上下文补取及适用条件检查 | 需要补检索时有限循环；简单查询直接调用知识服务 |
| 故障调查 Agent | 按平台、领域验证候选原因，选择受控取数和分析工具 | 是，受委派目标、输入范围及子预算限制 |
| 方案生成节点 | 根据已收集证据生成内部方案和客户回复 | 首版一次生成；由后续检查决定是否退回 |
| 经验提取节点 | 从有结果的工单提取候选经验 | 异步结构化处理，不因名称而增加 ReAct |

子任务委派包含目标、输入引用、允许工具、预算和完成条件；返回证据、发现、未解决项及停止原因。父编排负责最终流转，子 Agent 不能自行关闭工单、发消息或批准退款。子 Agent 不再递归派生 Agent。没有真实调查决策的角色仍叫节点或工具，不包装成独立 Agent。

### 4.3 编排、检索与检查的先后关系

编排 Agent 接收解析后的工单，先决定是否查询知识、查询反馈或请求补充。检索是它调度的动作，不放到“前置分诊”里。检索结果返回后，再执行证据检查；检查结果作为下一次编排的观察输入。

```text
请求解析 → 编排 → 检索／取数 → 结果检查 → 编排
                                      ├─ 追加调查
                                      ├─ 方案生成
                                      └─ HITL
```

所有工单走同一编排入口。简单咨询可能一次检索后即可形成方案；复杂故障才追加调查。不让前置分类器凭初始文字预测“复杂度”。

### 4.4 必要的模型判断是什么

代码检查负责确定性事项：字段是否齐全、接口状态、文档是否有效、已知型号是否匹配、预算是否耗尽。模型判断处理无法仅靠字段完成的语义问题，例如：片段是否回答当前问题、例外条件是否覆盖本工单、证据是否支持某个候选原因。

判定结果需要引用具体材料并说明缺口，例如“只找到 Android 方案，当前设备平台尚未确认”。模型自报的置信度、向量相似度或重排序分数，都不能单独等同于“答案正确”或“证据充分”。

第一阶段先以同一模型、不同任务提示词建立可定位问题的基线。轻量模型可用于解析和逐段相关性判断，较强模型可用于调查、跨证据分析；这是后续成本优化，不是架构前提。轻量模型的语义判断不确定时，允许请求更强模型复核；权限、预算等硬规则不得被更强模型推翻。

多轮对话、模型档位、工具调用循环是三个独立维度。使用更强模型不自动意味着进入 Agent；使用轻量模型也不妨碍运行有限的工具循环。

## 5. 知识服务与检索质量反馈

### 5.1 首版选择与替代方案

首版建立带型号、版本、来源和有效状态的文档型 RAG：解析→去重→按标题及条目切分→保留上下文→元数据→BM25／向量索引→候选融合→重排序→必要的相邻段补取→带引用回答。

选择理由：售后资料包含大量操作步骤、故障叙述和条件说明；现阶段没有证据证明跨文件声明冲突是主要失败来源。先建立强基线，避免把实体抽取、归一和合并错误同时引入主流程。

| 方案 | 适用点 | 成本与风险 |
|---|---|---|
| 文档型 RAG | 步骤、解释、故障叙述；入库相对简单 | 可能漏召回例外、混淆型号版本；仍需治理元数据 |
| 实体—属性—证据 | 规格、政策条件、版本适用性；显式管理重复与矛盾声明 | 抽取、消歧和冲突处理增加写入成本；遗漏属性或条件会影响召回与正确性 |

普通 RAG 不必然每次查询更贵；结构化也不保证查询更便宜。比较时计入首次入库、更新、查询、复核与维护成本。两者均存在上下文损失风险，证据回链无法补救未抽取或未召回的信息。

第二阶段以部分规格、保修条件、版本适用性为对象，比较“文档型 RAG”与“原文＋结构化声明”。不预先承诺全面迁移 KnowLoom，不以片段混乱本身作为迁移的充分理由。

### 5.2 检索后如何决定下一步

本方案借鉴“根据检索质量调整动作”的思路，不直接部署论文 CRAG 的训练模型或完整流程。原 CRAG 使用检索评估器指导后续动作，并包含外部搜索；本系统首版限定企业授权知识源，不因为企业资料缺失就用互联网替代内部政策。[CRAG 论文](https://arxiv.org/abs/2401.15884)、[作者实现](https://github.com/HuskyInSalt/CRAG)。

实现分为三层：

1. **元数据检查**：按型号、版本、地区、渠道、有效期过滤；未知条件保留为缺口。元数据缺失不能直接当作适用。
2. **片段语义评估**：模型接收问题、已确认事实和候选片段，输出相关性、适用条件、直接支持的内容、缺失项、冲突及证据引用。
3. **结果聚合与动作选择**：程序保留硬性阻断；知识调查 Agent 根据缺口选择有限的内部补救动作，最终返回编排节点。

```json
{
  "status": "partial",
  "evidence_refs": ["chunk_demo_17"],
  "supported_points": ["存在固件版本差异"],
  "missing_items": ["当前设备固件版本"],
  "conflicts": [],
  "suggested_action": "request_firmware_version"
}
```

`status` 是系统自定义状态，不是论文评估分数，也不是真实正确性的证明。建议包含 `sufficient`、`partial`、`no_evidence`、`conflicting`。

| 结果 | 可采取的动作 |
|---|---|
| 有适用且直接支持的材料 | 进入方案生成，再检查答案与证据一致性 |
| 只有部分条件或步骤 | 补取标题、相邻段或父段；必要时追问 |
| 相关材料未召回 | 保持原始意图，进行有限改写／别名扩展后重检索 |
| 型号或版本未知 | 从可信业务数据补取，或要求人工／用户确认 |
| 来源相互矛盾 | 展示冲突和来源，不能靠重复检索制造唯一答案；进入人工审核 |
| 补救耗尽仍无依据 | 标注无法确认，进入 HITL |

重排序判断相对相关性，不能证明材料包含答案。后续“问题—材料”检查判断证据覆盖，“答案—材料”检查判断生成是否越过证据，三者不混用。

**收益假设**：减少不相关材料下的直接作答，将检索失败转为补救或人工处理。**代价**：增加模型调用与延迟；评估器也会误判，可能拒绝正确材料或接受错误片段；改写可能偏离原意，反复检索可能形成无效循环。通过保留原问题、限制补救次数、展示证据与记录失败类型控制，收益需由实验确认。

### 5.3 可选的结构化声明实验

声明包含实体、属性、值、适用条件、有效时间、来源类型、文档版本、证据位置、生效状态。对新声明先归一实体和属性，检查适用范围是否重叠，再区分重复、补充、条件并存、版本替代、实质冲突和信息不足。

单值和多值属性分别定义比较规则；日期更新不自动覆盖旧值。范围不明、关系不清或来自经验的声明不能自动覆盖官方规格及政策。待审与失效状态要同时约束结构化查询和原文召回，防止从原文通道绕过治理。

## 6. 工单状态、执行与人工接管

### 6.1 工单状态与节点状态分离

| 工单状态 | 含义 |
|---|---|
| `QUEUED` | 已持久化并等待 Worker |
| `RUNNING` | 自动调查执行中 |
| `WAITING_HUMAN` | 自动处理暂停，人工待办已建立 |
| `WAITING_CUSTOMER` | 业务人员或渠道已请求客户补充／验证 |
| `PENDING_CONFIRMATION` | 已形成方案，等待业务审核或执行确认 |
| `RESOLVED` | 有明确反馈或人工确认的问题已解决 |
| `CLOSED_UNRESOLVED` | 人工关闭但未确认解决，保留原因 |

节点单独记录 queued/running/succeeded/failed/cancelled。节点失败或模型生成回复均不直接代表工单解决。

```text
QUEUED → RUNNING → PENDING_CONFIRMATION → WAITING_CUSTOMER → RESOLVED
             └→ WAITING_HUMAN → 补充后恢复 RUNNING／人工处理
运行异常或预算耗尽 → WAITING_HUMAN
人工可明确结案 → RESOLVED 或 CLOSED_UNRESOLVED
```

### 6.2 持久执行与预算

每次执行保存 run_id、节点输入输出引用、父子任务、模型／提示词／工具版本、耗时、Token、错误类型和 next_action。结构化状态保存已确认事实、候选原因、支持／反对证据、已做操作及待解决项；长日志保存在附件层，不整份塞入上下文。

Worker 领取任务时使用租约、心跳和状态版本控制；任务与状态先持久化，进程中断后从最近检查点恢复。人工修改后生成新的状态版本，旧运行的迟到结果不得覆盖新版本。

总预算包括调用次数、耗时、Token 和重复动作次数；子任务预算计入总预算。预算数值通过试跑确定，进入模型前由程序扣检。重复节点、同参数无新证据重试、非法动作分别处理；超过预算必须转 HITL，不能以“仍在思考”无限等待。

只读查询可有限重试并缓存；缓存键包含工单、工具参数、数据版本或时效范围，不能串用不同客户数据。对外发送等副作用使用幂等键与结果核对，不宣称 exactly-once。

### 6.3 HITL 是可操作节点

以下情况进入人工节点：关键资料缺失且无法补取、候选原因无法继续区分、来源冲突、工具持续失败、预算耗尽、没有合适工具、处理权限不足。模型异常和 Worker 失败也由系统触发人工兜底，不依赖模型主动选择人工。

进入人工节点时，LangGraph 先保存中断检查点，随后应用在业务事务内提交工单暂停状态、人工待办和检查点引用。官方 Saver 与业务事务不强行合并；中间崩溃由对账任务补齐待办，不能把图已暂停、页面却没有待办视为处理完成。具体一致性协议见 16.3。页面展示问题摘要、触发原因、已执行步骤、证据、待确认事项和可采取操作。

人工操作包括补充信息后恢复、修正事实后重跑指定节点、修改方案、转交负责人、人工结案。所有操作记录操作者、时间、变更内容及恢复起点。人工池支持未认领／已认领、优先级、等待时长和处理记录；通知用于提醒，待办本身必须可在列表中持续查询。

## 7. 日志与工具适配

工具统一返回 `status`、`data_refs`、`error_code`、`retryable`、`source`、`fetched_at`，由执行器检查参数并落库。至少区分：查询成功、确实无反馈、有反馈无附件、无适用时间数据、认证失败、超时、下载失败、解析失败。

“没有详细日志”且问题属于埋点支持范围时，才允许尝试 WiFi 埋点。接口调用失败不是没有日志；OTA、播放等问题不能因为取不到日志就输出连接类结论。已有详细日志时继续优先分析日志，FAQ 命中不能取代故障数据调查。

首版将现有脚本封装为反馈查询、日志下载、日志摘要／时间窗提取、WiFi 诊断、领域分析等受控能力。复杂领域的模型分析与可确定执行的解析规则分开，避免将文档里的分析方法误称为现成诊断 API。

附件与日志隔离存储，限制允许读取的路径。现有文档指出日志可能含 Authorization 等敏感字段；进入模型上下文、前端、经验库之前必须脱敏。前端显示与问题有关的证据片段，不显示账号口令、Token 或完整调试轨迹。生产与 Mock Adapter 明确分离，默认模拟环境不触发生产查询。

| 工单列表 | 状态、类型、优先级、负责人、来源、等待时长 |

节点图展示运行状态与分支，不要求第一阶段支持自定义拖拽流程。默认不将内部源码与日志证据整段发给客户。

### 8.2 一次处理示例

1. 业务人员填写“升级后反复断连”和邮箱，系统落库并排队。
2. 解析节点抽取症状及缺失项，编排派发知识与反馈调查；独立的只读子任务可并行。
3. 反馈查询返回多条记录，按设备与时间检查；无法确定关联时暂停并提示人工选择。
4. 日志出现连接与升级交叉线索，故障调查按需要调用两个领域工具。时间重合只是线索，不能直接证明因果。
5. 编排根据证据决定追加调查、形成方案或转 HITL。每一步都在时间线上可追踪。
6. 人工审核并记录客户反馈；成功确认后进入 RESOLVED，或继续补充调查。
7. 异步提取候选经验。工单关闭或生成建议本身不作为成功反馈。

### 8.3 交付顺序与验收

| 批次 | 交付 | 最小验收 |
|---|---|---|
| A | 工单、任务、节点、HITL 与 Mock Adapter | 创建、暂停、人工恢复、结案均落库；Worker 中断后可恢复 |
| B | 请求解析、文档 RAG、受控编排 | 咨询有引用；故障可追加调查；不支持的问题转人工 |
| C | 日志适配、领域诊断与证据输出 | 无日志和接口失败分开；不同客户与版本不串用 |
| D | 结果确认、经验候选、回放记录 | 可还原每次处理；经验可追到已确认结果 |

首版验收包含无依据问题、错误型号、接口超时、重复任务、预算耗尽、人工修改与迟到结果、Worker 重启等反例。具体准确率与性能阈值在样例集和基线建立后确定，不提前编造指标。

## 9. 第二阶段：消费者入口与渠道适配

### 9.1 App 客服问答与自动建单

消费者入口复用知识服务和调查能力，但单独设置交互时限与动作权限。普通咨询可自动答复；需要设备数据时关联已认证账号，不根据用户随意填写的邮箱直接暴露其他客户资料。

```text
用户在 App 提问 → 保存会话 → 解析与必要检索／调查
  ├─ 有适用证据且属于允许范围 → 自动回复 → 收集是否解决
  ├─ 需要补充 → 交互预算内追问；超时或无法继续则建人工工单
  └─ 无法处理／用户要求人工 → 持久化工单＋HITL 待办
                                         ↓
                              返回工单号与“已转人工”
                                         ↓
                              工作时间人工处理并回传
```

第一阶段中的工单从创建即存在；第二阶段可以先只有会话，在升级时关联或新建工单。若需要后台持续调查但尚未转人工，显示“已接收，正在处理”；不能提前显示“已转人工”。

先提交工单及待办事务，再通过可靠消息任务发送确认。落库失败不能返回“已记录”。每个会话的问题按幂等关联键建单，失败重试不重复生成工单；会话新问题与旧问题分别关联。客户离线不影响工单保存和人工处理。

确认回复包含工单号、当前状态和进度入口。“下一工作日处理”应由服务日历、值班时间和队列策略决定；未配置前使用“将在人工服务时间处理”，不承诺无法保证的回复时间。

### 9.2 渠道适配

优先自研 App，再接可用的咨询／电商接口；飞书可用于内部提醒、人工操作入口或内部需求采集。各平台能获取哪些消息、如何主动回复、是否支持附件和用户映射，需要按实际授权及接口能力核验。没有接口时以模拟事件或人工导入验证，不承诺读取全量聊天记录。

适配器统一输出 channel、event_id、conversation_id、sender_ref、occurred_at、text、attachments、reply_target。通过渠道与 event_id 去重；按会话、问题关联工单；乱序、编辑和补充信息作为新事件保留，避免简单地“一条消息一张工单”。

回复通过消息发送队列与 outbox 记录发送状态、平台回执和重试。发送失败不撤销已建工单；对外显示“已生成回复”和“已送达”时使用不同状态。

## 10. 经验沉淀与受控更新

系统的自进化限定为“基于反馈的经验提取、验证和检索复用”，不代表自动训练模型或任意改写系统指令。经验不取代企业知识库中的权威事实与政策。

第一阶段保存执行轨迹、结果反馈和候选经验，提供人工审阅；第二阶段补充去重、冲突检查、发布版本、经验召回及效果对照。

```text
结果确认／人工纠正 → 候选经验提取 → 脱敏与来源检查
       → 去重、适用条件与冲突检查 → 回放验证／人工审核
       → 发布版本 → 后续按条件检索 → 反馈、降级或撤回
```

经验保存问题特征、产品版本、触发条件、关键证据、有效及无效操作、反例／不适用条件、来源工单、结果确认方式和发布状态。失败案例也可保留，但标签须明确，不作为成功方案召回。

模型认为“处理成功”不是反馈。可接受来源包括客户明确确认、人工核验、或模拟环境的隐藏结果判定；三者分别标注。用户没有再回复不能直接标记解决。新经验不能自动覆盖官方政策；与权威材料冲突时进入审核。

经验只作为案例参考或排查提示，不能执行其中的任意文本指令。评测期间锁定经验版本，测试轨迹不自动写回正在评测的经验库。[Reflexion](https://arxiv.org/abs/2303.11366)提供反馈与经验复用的参考，本文不据此声称本系统效果已经改善。

## 12. Mock 数据与评测

### 12.1 Mock 数据构造

先定义故障／业务场景真值，再派生知识文档、客户设备、反馈记录、日志、用户措辞和后续反馈。所有引用一致，使用虚构身份和产品，不直接把真实客户资料复制为测试数据。

| 数据 | 要求 |
|---|---|
| 知识 | 含正常资料、重复、例外、版本差异、部分修订和真实无法回答的情况 |
| 反馈与日志 | 对齐设备、App 与固件版本、时间及反馈编号；覆盖无数据、下载失败等情况 |
| 工单与会话 | 含信息缺失、多意图、口语表述、补充、否定前述判断等变化 |
| 工具事件 | 可注入认证失败、超时、重复结果、乱序、发送失败 |
| 隐藏标签 | 必须证据、可接受方案、禁止结论、合理下一步、应否转人工、解决条件 |

隐藏真值与答案不进入 Agent 上下文；Mock 工具只返回当前动作允许看到的数据。先构造一小批可人工核对的完整场景，再扩展变体；不得把同一案例换个说法随机拆进积累集和测试集。Mock Adapter 与真实 Adapter 使用相同返回契约。

### 12.2 评测顺序

1. **闭环验证**：第一阶段先检查状态、证据、人工兜底、恢复和幂等，建立工单级回放。
2. **知识选型**：相同文档、问题、生成模型和预算设置下，比较文档 RAG 与原文＋结构化声明；分别报告普通问答、版本／条件、冲突／更新、无答案问题。
3. **编排价值**：固定知识方案，比较固定流程、全部进入调查 Agent、按证据缺口追加调查；不使用主观“简单／复杂”标签作为唯一正确答案。
4. **协作与模型成本**：对有代表性的复杂工单比较单调查 Agent 与集中委派的多角色方案；再比较同模型基线与轻量／较强模型配置，防止把模型差异误当成协作收益。
5. **经验机制**：冻结基础系统，比较无经验、直接检索历史案例、经筛选发布的经验；按场景族和时间分离积累集与测试集。

不同时改变知识结构、模型、编排和经验，避免收益无法归因。阈值与提示词在开发集调整，测试前锁定版本。通过少量人工复核校准模型评审；引用存在不代表证据支持，不能由同一模型自评作为唯一判据。

### 12.3 指标候选

| 维度 | 指标与解释 |
|---|---|
| 回答质量 | 正确性、适用条件正确率、关键证据覆盖、无依据结论比例 |
| 调查质量 | 完成必要验证的比例、错误关联日志、重复／无效工具调用 |
| 人工接管 | 应转人工而未转的比例、不必要转人工比例、交接材料完整性 |
| 工程闭环 | 落库与确认一致性、重复建单、恢复成功、迟到结果覆盖、消息回执 |
| 资源成本 | 入库／更新成本、每工单模型及工具成本、端到端耗时及分位数 |
| 经验效果 | 新场景处理变化、过期或不适用经验误用、无关场景退化 |

模拟环境报告“模拟案例处理结果”；模型首次回复、方案生成、人工接管、问题解决分别计时。模拟人工标签不等于真实客服效率，不沿用“2 小时降到 10 分钟”等未经测量的业务数字。

## 15. 第一阶段数据与接口契约

### 15.1 通用约定

主键使用 UUID，时间使用 PostgreSQL `timestamptz` 并以 UTC 存储，API 输出带时区的 ISO 8601，前端按 Asia/Shanghai 展示；客户故障时间同时保留原时区及精度，不能用不明时区的时间匹配日志。业务类型、状态和错误码使用统一枚举。JSON 使用 JSONB 保存可演进的结构，索引字段与状态独立成列。

人工写操作携带 `expected_version`；服务端用 `WHERE id=:id AND version=:expected_version` 更新，影响零行返回 409，不静默覆盖。记录事实来源和人工覆盖历史，人工修正值优先于旧模型抽取值。

run 状态固定为 queued/running/paused/succeeded/failed/superseded；人工待办为 unclaimed/claimed/resuming/completed/cancelled。工单与 run 状态分别维护：run 完成只表示自动执行结束，工单仍可待确认；工单终态必须同时完成或取消开放待办，清理活动执行指针。running 时请求结案先走停止协议，不在 Worker 仍有执行权时强行写终态。

允许的主要工单转移为 QUEUED→RUNNING；RUNNING→PENDING_CONFIRMATION/WAITING_HUMAN；人工恢复 WAITING_HUMAN→QUEUED；已联系客户后 PENDING_CONFIRMATION→WAITING_CUSTOMER；人工结案→RESOLVED/CLOSED_UNRESOLVED。未解决反馈从 WAITING_CUSTOMER 新建调查 run 并回 QUEUED；终态首版不开放任意重开 API。业务状态转移集中在 domain 状态机，API 与图节点不得各写一套。

## 16. LangGraph、状态一致性与恢复协议

### 16.1 图结构与状态契约

主图固定节点：`parse_request`、`supervisor`、`knowledge_investigation`、`fault_investigation`、`generate_solution`、`validate_solution`、`human_interrupt`、`finalize_run`。子图作为可观察的图节点接入；避免把全部子图隐藏在不透明工具函数内。编排输出必须经过 Pydantic 枚举和参数校验，再由条件边／Command 路由。

CaseState 至少包含：ticket_id/run_id/case_version、请求与事实来源、知识范围、候选原因、证据引用、已完成动作、未解决项、budget_usage、next_action、stop_reason。父图只接收子任务的结构化摘要和证据引用。子任务独立输出后由父节点合并，首版禁止两个子 Agent 同时写同一个事实字段。

`thread_id` 对应一次 run，命名空间由 run UUID 唯一确定，不能用邮箱或整个工单生命周期作唯一 thread。原 run 人工暂停后恢复保持 thread_id；重新调查或图版本不兼容则新建 run/thread。原始工具结果和模型调用保存执行版本；提示词改动不静默影响已经暂停的 run。

真实 Agent 执行前检查输入、工具权限与预算；子任务状态为 completed/partial/needs_human/error，返回 evidence_refs、findings、unresolved_items、stop_reason。无可用动作、两次相同动作且没有新事实或重复返回无进展时进入人工，不能仅依靠 LangGraph recursion_limit 防止死循环。

### 16.2 单 run 串行执行与检查点

首版每个 run 一次只允许一个 Worker 调用图。任务领取使用短事务与行锁，提交后再执行模型／HTTP 调用，不在业务事务里等待外部网络。

Worker 为该 run 建立独占检查点连接，在同一连接持有 run 级 PostgreSQL advisory lock，并由该连接的官方 PostgreSQL Saver 持久化检查点。P00 验证该组合在选定驱动版本下可用。检查点模式采用步骤间同步保存，优先保证恢复语义。该连接断开后停止整个执行，不透明重连同一旧执行继续写。

业务写入还要校验 lease_token 和 case_version。租约过期只说明需检查，不代表可以绕过仍被持有的 run 锁。新 Worker 必须取得锁后才能恢复；旧 Worker 失去执行权后的返回结果不得写业务状态。外部请求可能已经完成，恢复时先查 tool_executions 的逻辑动作记录和结果，再决定是否允许重试。

图检查点不保证所有外部请求只发生一次。副作用操作在 API 服务或幂等工具中完成；一期 Agent 工具全部只读。节点重放时，逻辑动作 ID 来自已保存的决策，不在每次重试重新生成随机 ID。

### 16.3 图暂停与人工待办的一致性

正常路径：图执行到 human_interrupt→保存中断检查点→Worker 读取暂停标识及 checkpoint_ref→业务事务写入 WAITING_HUMAN、paused run、human_task 和 ticket_event。human_task 以 run/pause_key 幂等。

独立对账循环定期扫描：执行租约过期、图已暂停但没有人工待办、图已完成但业务状态未投影、或 resume 动作已保存但任务未完成。对账先取得 run 锁，读取持久检查点，再幂等补齐业务状态，绝不通过重复完整调用 Agent 来“猜当前状态”。

业务事务提交失败时保留可恢复任务，不向前端报告成功转人工。若数据库整体不可用，系统只能返回可识别的故障，恢复后由对账补齐；不承诺在存储不可用时仍能成功建单。

### 16.4 人工恢复与修改

人工 resume 请求必须校验工单版本、认领权限、待办仍开放和引用仍可用。业务事务记录唯一 action_id、事实补充、版本增量、待办状态与 resume 任务。Worker 取得执行权后用同一 thread 调用 `Command(resume=...)`；节点从 interrupt 返回值读取人工动作并重新校验证据与预算。

LangGraph 的中断恢复可能从节点起点重放，不能把“恢复”理解成从任意 Python 行继续。human_interrupt 节点在 interrupt 之前不执行创建待办、发消息等非幂等动作。该行为依据官方中断文档，须通过 P02 故障试验验证。

重复 action_id 返回既有结果；不同 action_id 竞争同一版本返回 409。若故障发生在图已接受 resume、任务尚未完成之间，先查检查点／动作消费记录，再恢复后续执行，不能向下一个 interrupt 重复提交旧人工响应。

暂停点的小范围补充可同 run 恢复；替换已分析日志、修正关键型号／版本、退回早期阶段等操作，使用 reinvestigate：旧 run 标 superseded，新 run 从新 Case 快照开始，重新检查缓存适用性。首版不支持任意节点回滚。

运行中 takeover 先保存 cancel_requested，Worker 在可取消边界退出；页面显示“正在停止”。未释放 run 锁时不允许人工修改核心事实或启动新 run。外部调用设置超时，停止后由业务事务建立人工待办；同一 run 的迟到输出因执行权失效而被拒绝。

### 16.5 初始预算与错误处理

以下为可配置的调试初值，不是评测结论或业务 SLA：每次自动执行轮次最长 300 秒、最多 12 个只读工具逻辑动作、最多 20 次模型调用；知识改写最多 1 次、上下文补取最多 1 次、方案修改最多 1 次。图 recursion_limit 设为高于这些业务上限的最后保护，不用它替代业务预算。等待人工的时间不计入自动执行时长；人工恢复创建新的 budget_epoch 并保留历史累计用量，防止旧轮次已经耗尽预算导致恢复后立即再次中断。跨轮次硬上限单独配置，不因反复点击恢复而无限增长。

模型单次默认超时 45 秒；工具查询／下载按类型设超时，且不超过 run 剩余时间。只读调用最多 1 次瞬时错误重试，重试也记录耗时与调用预算。输入校验、认证失败、无数据不盲重试；429 按 Retry-After 与剩余预算处理。结构化输出非法只允许一次修复，仍非法转人工。实际数值在首次真实试跑后调整并保存 policy_version。

运行时以 budget_epoch 的剩余时间为准。并行子任务调用前通过共享预算预留调用数与最大输出额度，完成后对账实际 usage，失败与重试也记账；不允许每个子 Agent 各自使用一份未合并的“总预算”。

Token 总量与单次输出上限按选定模型明确配置，真实模式启动时缺少上限则拒绝运行。模型缺少可靠 usage 时标估算值，不填 0 冒充免费；估算不用于精确费用结论。预算耗尽或框架异常统一生成结构化停止原因和人工材料。

### 16.6 P02 固定 Mock 图的实现契约

固定图版本为 mock-v1，使用本章的节点名称，但由确定规则决定流转；设备或故障时间缺失时暂停，资料齐全时执行两个固定只读 Mock 调查并生成模拟方案。该流程用于工程恢复试验。P04 的兼容接入将两个内部步骤映射到注册工具、将方案生成接到统一 Mock Client，不改变节点、暂停或旧工具缓存键；真实 Supervisor、语义检索和日志调查分别按后续开发单元接入。

独立 Worker 领取任务采用短事务及 `FOR UPDATE SKIP LOCKED`；同一独占 psycopg 连接持有 run 会话锁并交给 PostgreSQL Saver。任务租约默认 30 秒，每约 10 秒心跳；检查点连接或执行权失效即结束当前尝试。业务投影按 ticket→run→task 顺序加锁，并校验 lease_token、有效租约、工单版本和活动 run。停止请求撤销旧 lease_token，后继 Worker 仍须取得 run 锁才能建立暂停，迟到方案不得写入工单。

连接健康探针与官方 Saver 后台写入共用 Saver 的连接锁，避免探针插入同一连接的 pipeline 临界区；该同步不替代运行锁、租约或业务版本检查。更换 Saver 版本须验证此连接使用契约。

独立 reconcile 循环扫描到期运行任务，只读取检查点并补齐节点/人工待办/方案投影，或重新排队未完成任务；它不调用整张图调查。Worker 接管任务后也先读取检查点，start 任务的已有暂停直接投影；resume 任务只有在原 pause_key 匹配且 action_id 尚未消费时提交 Command，已经消费则继续剩余节点。重复只读动作优先复用按 run/轮次/逻辑步骤确定的持久工具结果；节点时间线按完成的逻辑步骤幂等写入，不把物理重放次数报告为独立成功调用次数。

P02 Mock 预算初值为每轮 300 秒、24 个完成节点、至多 5 轮；真实工具/模型预算仍按 16.5 在后续阶段建设。每轮起点持久保存，崩溃重试不刷新同轮截止时间；等待人工之后恢复使用新轮次并保留历史。原始请求、人工事实来源、run/thread 和检查点均保留，图版本或检查点不兼容时只能人工处理或新建 run 重新调查。

业务迁移与检查点初始化仍为两个显式步骤：先 Alembic 兼容升级，再串行执行官方 Saver setup；Worker 不在启动时并发 setup。readiness 检查业务迁移版本、vector 和检查点表，liveness 不查询模型。P02 接口、命令和故障测试的实际结果记录在开发记录，不写进方案正文。

## 17. RAG、工具与页面实施细节

### 17.1 文档入库与混合检索

入库依次执行：文件格式／大小检查→原文及 checksum 保存→标题、条目与步骤识别→切块→元数据确认→embedding→构建 BM25 版本→发布可检索状态。初始块以完整条目为优先，长段按约 600～1000 中文字符切分，附约 100 字符相邻上下文；这些是起始参数，不能切断短步骤与标题后丢失归属。

文档 active 必须满足向量与关键词索引同一发布版本。BM25 用应用层中文分词，型号、错误码保留原始词项；按知识发布版本生成可重建快照。Worker 重启时校验快照与数据库版本，不一致则重建，不能默用旧索引。文档失效通过数据库过滤立即生效。

首版 BM25 与向量各取 20 候选，去重后按 RRF 融合，重排序取前 6 段，上下文数量还受 Token 预算约束。相关性分值不等于证据充分；回答前再次校验引用存在、来源有效及适用条件。未知型号／版本不直接使用某个特定版本答案，允许返回通用材料并明确缺口。

真实 embedding 与 rerank 通过 Provider 接口实现。前期未配置时仅运行 BM25 功能路径并显式标记 retrieval_mode，不称为完整混合检索；Mock Client 用于契约测试，不纳入效果报告。切换 embedding profile 需要重新入库生成向量，并保持旧 profile 可追溯。

P05 的 BM25 模式接受 multipart 的 UTF-8 MD/TXT 与元数据，文件上限 1 MiB、单行 4096 字符、最多 2000 片段；不支持的格式不入库。原始字节和 checksum 存 PostgreSQL，检索片段先做基础脱敏。适用产品、固件、地区、渠道必须显式提供，通用范围使用单独的 `*`；同一 doc_key/version 不允许改写内容或适用范围，重复上传复用原任务。

入库任务独立持久化，由专用 Worker 执行解析、切块、索引和发布；每任务有运行锁、租约与 token，阶段间续租，发布前再次检查期限。文档、片段、旧版本替换、知识发布版本和 BM25 快照在一个事务内提交。构建失败保留旧活动版本；失败任务保存阶段/错误码，暂时故障支持有界人工重试，源文件不可解析时上传新版本。归档取消未完成任务并撤销执行权，不能被迟到结果重新发布。

BM25 使用固定 `zh-bigram-v1` 分词（汉字单字与二元词项、完整型号与错误码），不是词典分词；参数 k1=1.2、b=0.75，采用正值 IDF。快照保存在数据库，检索检查算法/分词版本、发布版本、语料指纹和快照 checksum，不匹配则从有效片段重建。小规模原型用全量扫描和发布事务锁，暂不承诺大规模吞吐。显式 BM25 模式不生成假向量；切换混合模式须在 P06 满足相同发布版本和 profile 约束。

知识管理写接口仅供 knowledge_admin；内部 business/knowledge_admin 可检索和读取引用。返回全局索引版本、文档版本、原文 checksum、片段 hash、标题层级、行号、父段范围和相邻引用。查询按活动状态和适用范围/有效期过滤，条件未知时保留缺口而不选特定版本；历史引用可回源但标记不可用于当前回答。知识 API 与注册工具的数据库适配共用服务；固定 mock-v1 工单图保留兼容行为，自主知识调查在 P07 接入。

P06 接入契约：Provider 的公开配置包含端点、模型、角色覆盖、币种/费率版本、输入/输出上限和超时；密钥仅来自项目环境变量。聊天使用 JSON/schema 和引用白名单校验，最多一次修复；瞬时网络错误最多一次重试，每个物理请求独立预留共享预算并留审计。无可靠 usage 时用量/费用为 null，预留上界保留，不能以零费用展示；配置费率估算与供应商账单分开。

向量 profile 包含端点、模型、维度、预处理版本和执行模式；费用变化不要求重建，同维但不同模型也不得混用。片段/profile 唯一、维度匹配由 PostgreSQL 约束保证。构建在发布锁外调用 embedding，全部活动片段覆盖且语料版本未变才原子切换；失败保留旧索引，完成的 staging 向量可复用。新入库文档先按捕获的 profile 生成向量，再与片段/版本/关键词快照同事务发布；每次外部调用前续租，迟到结果不得越权发布。显式构建进程被终止后允许人工重跑，暂不提供自动构建对账。

混合检索使用 pgvector 精确余弦距离与 BM25 各20候选、RRF k=60、预算内可选重排，最多返回6段；网络请求期间不持发布事务锁，返回前检查发布版本/profile，变更即拒绝迟到结果。响应包含执行模式、profile、索引版本、候选数和供应商用量，业务 data_source 与模型 inference_mode 独立标记。固定 mock-v1 图继续保留旧检查点兼容，真实自主路由在 P07 接入。

真实接口小集使用独立本机验证库和公开虚构资料，默认共享额度5元、60次调用、50万Token、600秒；核验接口、结构、引用与追溯，不作为业务效果评测。无密钥时在建库和网络调用前明确停止；HTTP 模拟测试标记 contract，不能通过真实验收。供应商/模型基线可切换，公开配置与人工触发命令见 README，实际结果只记开发记录。

### 17.2 工具契约与反馈匹配

工具至少包括 search_knowledge、get_feedbacks、download_log、extract_log_window、diagnose_wifi、analyze_domain；后两项分别区分确定性规则与模型分析。输入输出均为 Pydantic 模型，允许工具列表与 schema 由代码维护。工具使用 customer_ref 和系统关联的邮箱，不能接受模型随意修改的其他客户邮箱。

反馈匹配先过滤设备／平台，再结合故障时间范围；证据不足则将候选列表提交人工确认。不能因为时间最近自动认定匹配。日志时间窗无法可靠定位时返回缺口和已查看范围，不把“没搜到”写成“没有发生”。

对工具返回声明 `data_source=mock/real`、来源记录 ID、查询条件和时间；该标记贯穿页面、证据、经验及评测。错误码包括 AUTH_FAILED、RATE_LIMITED、TIMEOUT、NO_FEEDBACK、NO_ATTACHMENT、NO_MATCHING_RECORD、DOWNLOAD_FAILED、PARSE_FAILED、UNSUPPORTED_DOMAIN。

P04 注册表只由代码维护，输入禁止额外参数；系统绑定 customer_ref/邮箱/当前设备，不能以模型传入的其他客户身份替换。下载只返回受控句柄与校验和；提取和分析只能使用当前会话已经授权的日志/窗口句柄，不接受磁盘路径或任意 URL。日志片段先脱敏再返回，源记录、查询和时间伴随结果；规则事件和模型分析明确区分。

统一模型接口按 parse、supervisor、solution、domain 角色选择 profile。确定性 Mock 实现仅提供方案与领域分析契约，其他角色不伪装成模型决策；真实供应商在 P06 接入。调用设置超时并校验 JSON/schema、数据模式和引用白名单，失败不得静默回落。Mock Token/费用保留 null，记录 simulated 和已完成逻辑节点的调用数，不宣称物理重放恰好一次。

场景回放使用公开 runtime 资料/动作脚本，工具和模型不读取 evaluation 标注；仅离线评测入口在执行后读取答案。12 个种子作为独立场景族管理；S11/S12 的工程故障点另运行真实测试库/Worker 进程检查。该回放验证契约与证据范围，不报告自主路由、诊断准确率或真实业务效果。本地代码边界不等于 OS ACL，部署时 Agent 仅挂载 runtime，评测进程另挂载 evaluation。

### 17.3 前端页面与刷新

P03 页面路由为 /login、/tickets、/tickets/new、/tickets/:id、/human-tasks。Pinia 仅保存登录会话，其他页面状态保留在组件内；HTTP 客户端统一处理 Cookie、CSRF、错误与取消。前端 API 类型由后端 OpenAPI 生成并提供一致性检查；详情响应增加 latest_run_id 和当前事实来源，终态清理活动指针后仍可查询最近运行。

页面正常轮询约 2 秒、后台约 30 秒，离开页面取消请求及定时器；使用 AbortSignal 拒绝过期响应覆盖新页面。事件按递增游标补取并去重；网络恢复立即刷新，断网暂停写操作。写请求超时 15 秒后显示结果未知，未确认的动作保持原 expected_version 和 action_id；409 保留本地草稿，用户显式刷新版本后才能重提。

Cookie 会话令牌不进入前端存储；CSRF 仅保存当前标签页 sessionStorage，首次页面恢复发现会话过期时也显示重新登录提示。草稿仅在当前组件生命周期内保存，不在跨账号或退出登录后自动恢复。P03 验收脚本用独立测试 API/前端端口和本机测试库，运行实际浏览器验证；不把浏览器用例结果当真实模型效果。

首版列表、详情、人工池每约 2 秒增量轮询；页面隐藏后退避，离开页面停止；恢复网络按 event_id 补取。先以 API 详情的工单状态为准，事件用于展示，不根据模型文字猜测状态。SSE 在二期有明确实时需求时增加，保留 GET 查询作为补偿。

详情固定展示：工单摘要、当前状态、节点时间线、关键事实与缺口、证据抽屉、内部方案、客户回复草稿、人工操作。时间线不展示长篇思维过程。人工操作提交 expected_version，409 时保留本地草稿并提示刷新，不自动覆盖。

一期方案审核通过仍是 PENDING_CONFIRMATION，只有业务记录“已联系客户并等待反馈”后才进入 WAITING_CUSTOMER；人工确认解决才转 RESOLVED。无外部发送接口时只提供复制草稿，不显示“已发送”。

| P12 | 渠道适配、服务日历、outbox 回传 | P11 | 优先自研 App；用模拟事件验证重复／乱序／发送失败，再接有权限的平台 |
| P13 | 经验发布召回与知识结构实验 | P09、P10 | 经验审核、版本撤回、检索适用条件；结构化声明只做可隔离的实验分支 |
| P14 | 对照评测、错误分析与简历证据 | P10；经验评测依赖 P13 | 固定数据与配置、输出分组结果和成本；只记录实际运行结论 |

最先交付 P00～P03 的“无真实模型也能跑通的工单闭环”，再把智能能力接入。不能先堆所有 Agent，最后才补工单状态和人工恢复；也不以只会调用模型 API 作为一期完成。

每一单元的记录至少包含：变更文件、接口／迁移变化、执行的验证命令与结果、剩余限制。迁移采用新增与兼容变更，未经确认不删除已有数据；迁移失败先定位，不自动重建或清空数据库。

## 19. 验收场景与验证命令规划

### 19.1 第一批 12 个种子场景

以下是拟构造的场景，不是已有评测结果；一个场景可以有多种措辞，但同场景族不可跨积累集和测试集泄漏。

| ID | 输入／异常 | 必须观察到的结果 |
|---|---|---|
| S01 | 明确型号的规格咨询 | 引用适用资料生成方案，不无故取客户日志 |
| S02 | 型号缺失，资料随版本不同 | 输出缺口，不能擅选型号；人工补充后继续 |
| S03 | 行驶中连接失败，有匹配日志 | 日志证据与处理建议对应，能回看来源 |
| S04 | 熄火断连，FAQ 与日志均存在 | 两类证据合并，不能跳过应做的日志调查 |
| S05 | 升级后断连，需连接与 OTA 交叉调查 | 可委派两个领域，时间相关不直接写因果 |
| S06 | 确认没有日志，仅连接埋点 | 合理降级且标来源 |
| S07 | OTA 故障没有日志 | 不用 WiFi 埋点伪造 OTA 根因，进入人工 |
| S08 | 查询超时／认证失败 | 区分失败与无数据，有限重试或转人工 |
| S09 | 同邮箱多设备、多反馈 | 不串用记录，必要时让人工选择 |
| S10 | 相同适用范围的政策相互矛盾 | 展示冲突并接管，不靠模型自信消解 |
| S11 | 人工补充、重复点击、运行迟到结果 | 版本与幂等生效，只有一个有效后继任务 |
| S12 | 预算耗尽、Worker 崩溃／检查点与待办间崩溃 | 无无限循环，重启对账后有可操作待办或正确恢复 |

S11/S12 细分故障注入点：任务提交后响应前、工具返回后检查点前、中断保存后待办提交前、人工动作提交后执行前、resume 生效后完成记录前、租约过期但旧执行尚未退出。每个点验证“无静默丢单、无旧结果覆盖、无重复人工待办”，不把重复只读请求误称为业务副作用已重复执行。

### 19.2 测试层次与目标命令

以下命令是开发完成后应提供的入口，现在不声称已经存在或通过。

| 层次 | 目标入口 | 范围 |
|---|---|---|
| 后端规则／服务 | `python -m pytest tests/unit` | 状态机、版本、预算、匹配、脱敏、引用检查 |
| PG 与图集成 | `python -m pytest tests/integration` | 真实测试库、Saver、任务争抢、中断、恢复与一致性 |
| 前端 | `npm run typecheck`、`npm run test:unit`、`npm run build` | 类型、关键人工操作与构建；低价值展示不堆测试 |
| 工单闭环 | `npm run test:e2e` | Playwright 创建、接管、恢复、确认与错误提示 |
| 固定场景回放 | `python -m app.eval replay --suite smoke` | Mock 可重复闭环；真实模型效果另用版本化实验配置 |
| 基础设施 | `docker compose config`、迁移检查、`/health/live` 与 `/health/ready` | 配置、数据库／图必要依赖、schema 版本；不在 liveness 调昂贵模型 |

SQL 约束、租约和锁测试必须在 PostgreSQL 上运行，不以 SQLite 通过替代。测试库与开发库分开；清理仅限测试自己创建且核对过的对象，不清空真实数据。验证流程在 CI 中先做 lint/typecheck、unit、integration、build，再执行关键 e2e；外部模型实验单独触发，避免 CI 消耗不可控。

## 20. 执行准入与阶段性交付

第一阶段开工前，用户已确定的技术栈不再反复询问。可以先做 P00～P03 的本地 Mock 闭环；模型供应商、真实接口和渠道权限作为后续接入条件，不把它们伪装成已完成能力。

开发时若发现依赖版本不兼容、正式接口字段与假设不符或恢复语义无法满足，应先给出复现与影响，更新对应契约后再改实现。第一阶段不扩展自由聊天、全渠道、自动退款、全量实体知识库、自动改系统提示词等范围。

实现从 P00 环境与框架试验开始，先展示验证结果，再进入 P01；不跳过中断／恢复试验直接搭完整多 Agent 系统。开发进度与验收证据独立记录，不写入技术方案正文。
